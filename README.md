# SDN-Based Online Examination Network

## 1. Overview

This project implements an online examination system using C socket programming and Software-Defined Networking (SDN).

The application uses TCP sockets for communication between examination clients and the examination server. An SDN controller manages network forwarding and provides programmable network controls, including manual IP blocking and traffic-based detection.

The network is emulated using Mininet and Open vSwitch.

This is an educational prototype intended to demonstrate socket programming, concurrent client handling, SDN-based network control, and network performance evaluation.

## 2. Objectives

- Implement a client-server application using TCP sockets in C.
- Support multiple examination clients through concurrent server-side threads.
- Implement a text-based examination protocol.
- Emulate a network containing multiple clients and an examination server using Mininet.
- Use an SDN controller to manage forwarding and enforce network policies.
- Support manual IP blocking and unblocking.
- Detect unusually high packet rates and automatically block qualifying source IP addresses.
- Evaluate application and network performance under different conditions.

## 3. Architecture

### Application Layer

The examination application consists of:

- **Server (`src/server.c`):** Accepts client connections, manages student sessions, presents questions, records answers, and calculates examination scores.
- **Client (`src/client.c`):** Connects to the server, identifies the student, displays questions, accepts commands and answers, and submits the examination.

The application uses TCP for reliable, ordered communication.

The server supports concurrent client sessions using threads.

### SDN Control Layer

- **Controller (`sdn/exam_controller.py`):** Uses OS-Ken and OpenFlow 1.3 to manage forwarding rules, block source IP addresses, collect flow statistics, and perform packet-rate-based detection.
- **Topology (`src/topology.py`):** Creates the Mininet network and connects the Open vSwitch switches to the remote controller.

### Network Topology

The emulated network contains:

- Two Open vSwitch switches: `s1` and `s2`
- Three client hosts: `h1`, `h2`, and `h3`
- One examination server host: `server`
- One inter-switch link between `s1` and `s2`

Host addressing:

| Host | IP address | Connected switch |
|---|---|---|
| h1 | 10.0.0.1/24 | s1 |
| h2 | 10.0.0.2/24 | s1 |
| h3 | 10.0.0.3/24 | s2 |
| server | 10.0.0.10/24 | s2 |

The examination server listens on TCP port `8080`.

The controller uses the following ports:

| Purpose | Address | Port |
|---|---|---|
| OpenFlow connection | 127.0.0.1 | 6653 |
| Local controller control interface | 127.0.0.1 | 8765 |

## 5. Prerequisites

The project is intended for a Linux environment with:

- GCC
- GNU Make
- Mininet
- Open vSwitch
- Python 3
- OS-Ken
- OpenFlow 1.3 support

Mininet and Open vSwitch must be installed and operational.

OS-Ken must be installed in the Python environment used to launch the controller. The supplied controller startup script activates the project's `.venv-sdn` virtual environment.

The project scripts assume that the repository is located at:

```text
~/online-exam-network
```

If the repository is stored elsewhere, update the `PROJECT_DIR` setting in the scripts accordingly.

From the project directory, compile the client and server:

```bash
cd ~/online-exam-network

```

```bash

```

## 7. Running the System

The controller, Mininet topology, examination server, and examination clients run as separate components.

### Terminal 1: Start the SDN Controller

Run:

```bash
cd ~/online-exam-network
./scripts/start_controller.sh
```

The script activates the `.venv-sdn` virtual environment and starts OS-Ken with OpenFlow listening on port `6653`.

Keep this terminal open while using the network.

### Terminal 2: Start the Mininet Topology

Open a second terminal and run:

```bash
cd ~/online-exam-network
./scripts/start_topology.sh
```

The script launches the Mininet topology with elevated privileges.

Keep the Mininet CLI open while using the network.

### Inspect the Network

Inside the Mininet CLI, check connectivity using:

```text
pingall
```

You can also run commands on individual hosts by prefixing them with the host name. For example:

```text
h1 ping -c 3 10.0.0.10
```

### Terminal 3: Start the Examination Server

Inside the Mininet CLI, start the server on the designated server host:

```text
server /home/malay-parmar/online-exam-network/server
```

The server listens on TCP port `8080`.

If your project directory differs, use the corresponding absolute path.

### Start an Examination Client

In the Mininet CLI, start a client on a client host:

```text
h1 /home/malay-parmar/online-exam-network/client 10.0.0.10
```

Additional clients can be started on `h2` and `h3`.

Each client should use a distinct student ID for concurrent sessions.

Follow the client prompts to identify the student, start the examination, navigate questions, submit answers, and finish the session.

**Note:** The commands above invoke the compiled binaries directly using their absolute paths. The `scripts/run_app.sh` helper is also provided, but its behavior inside Mininet hosts must be verified before relying on it.

## 8. Controller Control Interface

The controller exposes a local TCP control interface on `127.0.0.1:8765`.

The supported commands are:

| Command | Purpose |
|---|---|
| `STATUS` | Display controller status and traffic-detection information |
| `BLOCK <IP>` | Request blocking of a source IP address |
| `UNBLOCK <IP>` | Request removal of a source IP block |

Commands use a newline-terminated text protocol.

For example, to request the status from the Ubuntu host, use a TCP client that can send a newline-terminated command to `127.0.0.1:8765`.

If Netcat is available, a status request can be sent with:

```bash
printf 'STATUS\n' | nc 127.0.0.1 8765
```

To request blocking of `h1`:

```bash
printf 'BLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
```

To remove that block:

```bash
printf 'UNBLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
```

These commands are examples of the control protocol. Their behavior and output should be confirmed during the documented test procedure.

The control interface is intended for local project use and should not be exposed to untrusted networks.

## 9. Traffic Detection and Network Policies

The controller periodically collects OpenFlow flow statistics and calculates packet rates from changes in packet counters.

The current configuration uses:

- **Statistics polling interval:** 2 seconds
- **Packet-rate threshold:** 1,000 packets per second
- **Excluded source IP:** `10.0.0.10` (the examination server)

When a qualifying source flow reaches the configured threshold, the controller can automatically block its source IP address.

The threshold is a configurable project parameter, not a universal definition of malicious traffic. Legitimate high-throughput traffic may also exceed it.

The effectiveness of the detection mechanism, including false positives and recovery behavior, should be evaluated using controlled test cases.

The throughput measurements describe the configured Mininet topology,
not a physical production network. They should not be generalized beyond
the tested setup.

Further controlled testing is needed to establish automatic-blocking
behavior, false-positive rates, recovery behavior, unaffected-client
isolation, and bandwidth-limiting performance. These features should
not be described as fully verified unless supported by recorded test
evidence.

## 11. Limitations and Security Considerations

- Student IDs provide session identification but do not constitute a complete authentication system.
- Packet-rate-based blocking may classify legitimate high-throughput traffic as suspicious.
- The current traffic threshold may require calibration for different workloads.
- The project is an educational prototype and should not be deployed as a production examination platform without additional authentication, security, reliability, and operational controls.
- Performance results from Mininet describe the emulated environment and should not be interpreted as physical-network performance.
