# SDN-Based Online Examination Network

## Get the project

Clone the maintained repository and enter the checkout:

```bash
git clone https://github.com/malayparmar-dev/online-exam-network.git
cd online-exam-network
```

To update an existing checkout to the latest `main` revision:

```bash
git pull --ff-only
```

## 1. Overview

This project implements an online examination system using C socket programming and Software-Defined Networking (SDN).

The application uses TCP sockets for communication between examination clients and the examination server. An SDN controller manages network forwarding and provides programmable network controls, including manual IP blocking and traffic-based detection.

The network is emulated using Mininet and Open vSwitch.

This is an educational prototype intended to demonstrate socket programming, concurrent client handling, SDN-based network control, and network performance evaluation.

## 2. Objectives

- Implement a client-server application using TCP sockets in C.
- Support multiple examination clients through concurrent server-side threads.
- Implement a text-based examination protocol.
- Emulate a network containing multiple clients and an examination server using Mininet.
- Use an SDN controller to manage forwarding and enforce network policies.
- Support manual IP blocking and unblocking.
- Detect unusually high packet rates and automatically block qualifying source IP addresses.
- Evaluate network response time and throughput fairness under shared-link load.

## 3. Architecture

### Application Layer

The examination application consists of:

- **Server (`src/server.c`):** Accepts client connections, manages student sessions, presents questions, records answers, and calculates examination scores.
- **Client (`src/client.c`):** Connects to the server, identifies the student, displays questions, accepts commands and answers, and submits the examination.

The application uses TCP for reliable, ordered communication.

The server supports concurrent client sessions using threads.

### SDN Control Layer

- **Controller (`sdn/exam_controller.py`):** Uses OS-Ken and OpenFlow 1.3 to manage forwarding rules, block source IP addresses, collect flow statistics, and perform packet-rate-based detection.
- **Topology (`src/topology.py`):** Creates the Mininet network and connects the Open vSwitch switches to the remote controller.

### Network Topology

The emulated network contains:

- Two Open vSwitch switches: `s1` and `s2`
- Three client hosts: `h1`, `h2`, and `h3`
- One examination server host: `server`
- One inter-switch link between `s1` and `s2`

Host addressing:

| Host | IP address | Connected switch |
|---|---|---|
| h1 | 10.0.0.1/24 | s1 |
| h2 | 10.0.0.2/24 | s1 |
| h3 | 10.0.0.3/24 | s2 |
| server | 10.0.0.10/24 | s2 |

The examination server listens on TCP port `8080`.

The controller uses the following ports:

| Purpose | Address | Port |
|---|---|---|
| OpenFlow connection | 127.0.0.1 | 6653 |
| Local controller control interface | 127.0.0.1 | 8765 |

## 5. Prerequisites

The project is intended for a Linux environment with:

- GCC
- GNU Make
- Mininet
- Open vSwitch
- Python 3
- OS-Ken
- OpenFlow 1.3 support
- `iperf3` for network experiments

Mininet and Open vSwitch must be installed and operational.

OS-Ken must be installed in the Python environment used to launch the controller. The supplied controller startup script activates the repository's `.venv-sdn` virtual environment. The scripts locate the repository from their own location, so the checkout can be placed anywhere.

### Fresh Ubuntu setup

Install the system packages needed to build the C application and run the Mininet topology:

```bash
sudo apt update
sudo apt install build-essential mininet openvswitch-switch python3 python3-venv iperf3 netcat-openbsd
```

From the root of the cloned repository, create the controller environment and install OS-Ken:

```bash
python3 -m venv .venv-sdn
.venv-sdn/bin/python -m pip install --upgrade pip
.venv-sdn/bin/python -m pip install -r requirements-sdn.txt
```

The controller uses this virtual environment. The topology is launched with the system `python3` so it can use Ubuntu's Mininet installation. The pinned controller dependencies were recorded from the project environment; use Python 3.12 or newer. Ensure Open vSwitch is running before starting a topology. Package installation needs access to Ubuntu package repositories and the Python package index.

## 7. Running the System

The controller, Mininet topology, examination server, and examination clients run as separate components.

### Terminal 1: Start the SDN Controller

Run:

```bash
./scripts/start_controller.sh
```

The script activates the `.venv-sdn` virtual environment and starts OS-Ken with OpenFlow listening on port `6653`.

Keep this terminal open while using the network.

### Terminal 2: Start the Mininet Topology

Open a second terminal and run:

```bash
./scripts/start_topology.sh
```

The script launches the Mininet topology with elevated privileges.

Keep the Mininet CLI open while using the network.

### Inspect the Network

Inside the Mininet CLI, check connectivity using:

```text
pingall
```

You can also run commands on individual hosts by prefixing them with the host name. For example:

```text
h1 ping -c 3 10.0.0.10
```

### Terminal 3: Start the Examination Server

Inside the Mininet CLI, start the server on the designated server host:

```text
server ./server
```

The server listens on TCP port `8080`.
The topology startup script runs from the repository root, so `./server` and `./client` refer to binaries in this checkout.

### Start an Examination Client

In the Mininet CLI, start a client on a client host:

```text
h1 ./client 10.0.0.10
```

Additional clients can be started on `h2` and `h3`.

Each client should use a distinct student ID for concurrent sessions.

Follow the client prompts to identify the student, start the examination, navigate questions, submit answers, and finish the session.

The topology starts from the repository root, which is shared by the Mininet hosts. The helper `scripts/run_app.sh` can also launch a host binary from the project root. Student IDs must be unique among active sessions.

### Step-by-step live demonstration

This walkthrough shows the student experience and the controller's manual policy in real time. It assumes the Ubuntu setup above is complete and the controller and topology are not already running. `xterm` is needed for separate interactive host terminals; install it if necessary:

```bash
sudo apt install xterm
```

1. **Build and check the application** from the repository root:

   ```bash
   make
   make test
   ```

2. **Start the SDN controller** in Terminal 1 and leave it running:

   ```bash
   ./scripts/start_controller.sh
   ```

3. **Start Mininet** in Terminal 2:

   ```bash
   ./scripts/start_topology.sh
   ```

   At the `mininet>` prompt, check connectivity:

   ```text
   pingall
   ```

   The expected result is 0% packet loss.

4. **Start the examination server** in the Mininet CLI. It runs in the background so the CLI remains available:

   ```text
   server ./server > /tmp/exam-server-demo.log 2>&1 &
   ```

5. **Open two interactive client terminals** from the Mininet CLI:

   ```text
   xterm h1 h2
   ```

   In each new terminal, run:

   ```bash
   ./client 10.0.0.10
   ```

   Enter different student IDs and type `START`. On question 1, answer `A` and then change it to `B` to show answer replacement; the final answer is the one scored. Use `N` and `P` to navigate, a number from `1` to `5` to jump to a question, and `S` then `YES` to submit. The client prints the result and score. Running both terminals demonstrates simultaneous independent sessions. You can open a third with `xterm h3` and repeat with another ID.

   To show the application event log after submission, use a repository-root shell:

   ```bash
   tail -n 12 results/app_metrics.csv
   ```

   It records connection, start, question, answer, submission, and disconnect events. The server enforces the exam deadline; the full timer behavior is covered by `make test` and does not have a live client countdown display.

6. **Inspect live controller state** from Terminal 3 (the ordinary Ubuntu shell, not the Mininet CLI):

   ```bash
   printf 'STATUS\n' | nc 127.0.0.1 8765
   ```

   The response includes connected switches, active blocks, the polling interval, and the automatic-block threshold.

7. **Demonstrate manual blocking and recovery.** From Terminal 3, block h1:

   ```bash
   printf 'BLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
   ```

   At `mininet>`, compare reachability:

   ```text
   h1 ping -c 2 -W 1 10.0.0.10
   h2 ping -c 2 -W 1 10.0.0.10
   ```

   h1 should be blocked while h2 remains reachable. Unblock h1 from Terminal 3:

   ```bash
   printf 'UNBLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
   ```

   Then repeat the h1 ping to show recovery. The automated network validation additionally checks that a blocked h1 exam TCP connection is denied, h2 can complete an exam during the block, and h1 can complete an exam after recovery.

8. **Finish the live topology** by closing the client terminals and entering `exit` at `mininet>`. Stop the controller with Ctrl+C in Terminal 1.

For the traffic-triggered automatic block, shared-link congestion measurements, and saved performance report, use the automated experiment in [Testing and Performance Evaluation](#10-testing-and-performance-evaluation). It runs scripted checks and prints a summary; it is not an interactive student exam window. Run it after exiting the manual topology so it can create a fresh Mininet network. It starts its own controller if none is running, or reuses one already listening on both controller ports.

For a local loopback demo without Mininet, use two terminals from the repository root:

```bash
./scripts/run_app.sh server
```

```bash
./scripts/run_app.sh client 127.0.0.1
```

The default server port and exam duration are 8080 and 300 seconds. `EXAM_PORT`, `EXAM_DURATION_SECONDS`, and `EXAM_METRICS_FILE` can override these values for isolated tests. The server writes timestamped CSV events to `results/app_metrics.csv` by default; the generated file is ignored by Git.

## 8. Controller Control Interface

The controller exposes a local TCP control interface on `127.0.0.1:8765`.

The supported commands are:

| Command | Purpose |
|---|---|
| `STATUS` | Display controller status and traffic-detection information |
| `BLOCK <IP>` | Request blocking of a source IP address |
| `UNBLOCK <IP>` | Request removal of a source IP block |

Commands use a newline-terminated text protocol.

For example, to request the status from the Ubuntu host, use a TCP client that can send a newline-terminated command to `127.0.0.1:8765`.

If Netcat is available, a status request can be sent with:

```bash
printf 'STATUS\n' | nc 127.0.0.1 8765
```

To request blocking of `h1`:

```bash
printf 'BLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
```

To remove that block:

```bash
printf 'UNBLOCK 10.0.0.1\n' | nc 127.0.0.1 8765
```

These commands are examples of the control protocol. Their behavior and output should be confirmed during the documented test procedure.

The control interface is intended for local project use and should not be exposed to untrusted networks.

## 9. Traffic Detection and Network Policies

The controller periodically collects OpenFlow flow statistics and calculates packet rates from changes in packet counters.

The default configuration uses:

- **Statistics polling interval:** 2 seconds
- **Automatic-block threshold:** 5,000 packets per second
- **Excluded source IP:** `10.0.0.10` (the examination server)

When a qualifying source flow reaches the configured threshold, the controller blocks its source IP address. The threshold and polling interval can be overridden with `EXAM_AUTO_BLOCK_PPS` and `EXAM_STATS_INTERVAL` when starting the controller. The threshold avoids treating ordinary traffic on the emulated 10 Mbps host links as a high-rate burst, but it still requires calibration for other environments.

The threshold is a configurable project parameter, not a universal definition of malicious traffic. Legitimate high-throughput traffic may also exceed it. The batch network check generates a controlled small-datagram burst, verifies that only the source client is blocked, then unblocks it and checks recovery.

## 10. Testing and Performance Evaluation

Historical and intermediate reports under `results/` are retained as evidence from earlier implementation stages. The latest successful full network run is `results/network_validation_20261025_150625.txt`. It includes two exam clients through Mininet, SDN denial and recovery, congestion measurements, and response-time and fairness results. Its provenance section records the Git base and hashes of the local source files used by the run. See [`results/README.md`](results/README.md) for which reports are authoritative and which are historical.

### Reproducing the tests

Run the C protocol and application acceptance suite from the project root:

```bash
make test
```

These tests use a private loopback port, a short test timer, and a temporary metrics file. They do not need Mininet or elevated privileges. The same checks run in GitHub Actions on Ubuntu 24.04.

The current application test suite covers protocol framing and oversized-line recovery, the interactive C client, all exam questions, answer replacement, question navigation, invalid answers and commands, exam abandonment, ten concurrent isolated sessions, slow handshakes, duplicate IDs, timed finalization, and application metrics. `make test-controller` checks the controller control socket; full OpenFlow policy and performance acceptance requires the Mininet experiment.

After installing `.venv-sdn`, run `make test-controller` to start an isolated temporary OS-Ken controller and verify status, configuration, malformed input, server-IP protection, manual block, and unblock without Mininet.

Run the full network experiment, which starts an OS-Ken controller if its ports are free and requires sudo permission to create the Mininet topology. Authenticate in the same terminal first; the script uses the cached sudo ticket:

```bash
sudo -v
./scripts/run_network_validation.sh
```

This test checks the real C exam server and two TCP clients across the Mininet topology, measures three baseline samples for each of the cross-switch and same-switch paths, then runs three synchronized h1/h2 TCP load trials over the shared link. Each trial records both receiver throughputs, Jain's fairness index, and h1's average ICMP round-trip time; a no-load h1 RTT is recorded for comparison. A fairness index of 1 means equal measured throughput, while lower values mean greater imbalance. These are network RTT measurements, not application-server processing latency; the server's CSV separately records request processing latency. The experiment also checks automatic source blocking against the exam TCP service, confirms an unaffected client can complete an exam, then unblocks h1 and verifies recovery. Reports and raw output are written under `results/`. The script reuses a controller only when both configured controller ports are already listening; it does not stop a pre-existing controller.

The latest run recorded a 19.572 ms baseline h1 RTT and 302.447 ms average RTT during shared-link load. Three concurrent trials measured Jain fairness of 1.0000 each, with both h1 and h2 averaging about 2.254 Mbps. These results apply only to this Mininet topology; use the report's provenance section when comparing them to later runs.

`./scripts/run_all.sh --app-only` runs the non-privileged checks only. `./scripts/run_all.sh` runs both application and network checks.

### Interpreting the results

The throughput, RTT, and fairness measurements describe the configured
Mininet topology, not a physical production network. They should not be
generalized beyond the tested setup.

Mininet measurements describe this emulated topology, not a physical production network. Repeated trials reduce noise but do not establish general performance claims. The automatic blocker is a configurable lab policy; thresholds must be calibrated before use with other traffic.

## 11. Limitations and Security Considerations

- Student IDs provide session identification but do not constitute a complete authentication system.
- Packet-rate-based blocking may classify legitimate high-throughput traffic as suspicious.
- The current traffic threshold may require calibration for different workloads.
- The project is an educational prototype and should not be deployed as a production examination platform without additional authentication, security, reliability, and operational controls.
- Performance results from Mininet describe the emulated environment and should not be interpreted as physical-network performance.
